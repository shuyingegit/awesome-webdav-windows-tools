# 把 NAS 挂成 Windows 盘符之后，容量和状态栏为什么经常骗你

> 说明：本文整理的是我在 Windows 10/11 + 群晖 DS920+ 上把 NAS 通过 WebDAV 挂成盘符之后实际遇到的几个显示层问题。不同 NAS、不同挂载器的表现会有差异，遇到类似现象先按本文的办法确认一遍。

## 一、属性窗口里的「可用空间」不是实时值

挂载成盘符之后，在资源管理器里右键盘符 → 属性，容量那一栏通常是个很整齐的数字：总容量几十 TB、可用空间几百 GB。可这个数字往往不是 NAS 端文件系统算出来的，而是挂载器自己上报的一个估算值。

结果是：

- 你在 NAS 上删掉了 100 GB 的视频，Windows 里「可用空间」纹丝不动；
- 你在 Windows 里往盘符里写了 50 GB 的东西，NAS 的存储管理器里配额也没有立刻变化；
- 明明 NAS 上还有大把空间，Windows 却提示「磁盘空间不足」。

我的做法是不看属性窗口的容量，而是直接看 NAS 控制面板里卷的剩余空间，以及挂载器自己的状态面板（如果有）。属性窗口的容量只当参考。

## 二、状态栏的传输速度在挂起时会归零

往盘符里复制大文件时，状态栏的速度数字是挂载器在实时汇报的。但只要出现下面任一情况，这个数字就会掉到 0 KB/s，而且往往不会自动恢复：

1. NAS 休眠了；
2. 交换机端口做了节能（Green Ethernet / EEE）；
3. 路由器上的 QoS 或防火墙连接跟踪表满了。

第 3 种最隐蔽：表现为「大文件传到 90% 卡住，小文件正常」。解决顺序是先确认 NAS 本身还在响应（浏览器里打开它的管理界面），再检查网络设备，最后才回到挂载器配置。UEFI 机器上顺手把网卡的 EEE 关掉，能省掉一类假死。

## 三、文件句柄的释放时机和 SMB 不一样

这是我认为 WebDAV 和 SMB 最大的差别。SMB 有相对明确的句柄回收机制，而 WebDAV 走的是 HTTP 加锁，很多挂载器在实现上并不严格。

实际表现：

- 在资源管理器里删掉一个正被程序打开的文件，删除动作「成功」，但 NAS 上的文件还在，磁盘空间也没释放；
- 程序报「设备未就绪」而不是「文件正在使用」；
- 重启挂载器之后，之前那些「已删除」的文件又出现了。

排查这类问题的顺序是：先在 NAS 上看文件是否真的消失，再看挂载器的句柄列表，最后才重启客户端。养成「先确认服务端状态」的习惯，能省掉大量无效的重装。

## 四、大文件整块传输带来的断点代价

WebDAV 客户端普遍按固定分块上传，默认 4 MB 到 16 MB 不等。好处是进度条平滑，坏处是网络抖一下就要重传整个分块。

如果你的链路是家宽上行、或者公司 WiFi，丢包率稍微高一点，一个 20 GB 的文件传到一半失败，重传代价就相当可观。值得做的调整有两个：

1. 把分块大小调大（如果挂载器允许），减少请求次数；
2. 用支持断点续传的工具做大批量传输，而不是靠资源管理器直接拖拽。

## 五、怎么判断「挂载成功」

一个可靠的检查顺序：

1. 在盘符里新建一个空目录，能创建说明写权限正常；
2. 往里写一个小文件，再读回来比对内容，能读回说明读写一致；
3. 记录这个文件的修改时间是否正确；
4. 重启挂载器（不是重启电脑），确认映射还在。

前两步能过，说明基本可用；第四步是很多工具翻车的地方——很多挂载器默认开机不自动恢复映射，看起来像「盘符丢了」。

## 六、什么场景值得换成别的方案

我用的挂载器是 ScsDrive（官网 https://drive.scsoi.com），它做的事情就是把 WebDAV / NAS 挂成设备级的真实本地盘符，下面的现象是它和同类工具共有的。

如果你的核心需求是「把 NAS 当成本地盘用，且对大文件吞吐和断点续传有要求」，那 WebDAV 未必是最优解：SMB 的句柄语义更成熟，分块行为也更可控。

而如果你的需求偏「读多写少、目录结构深、想要一个稳定盘符入口」，WebDAV 挂载的便利性就体现出来了——它不需要额外的驱动层，配置项少，跨网络环境也能用。

两种方案没有绝对优劣，取决于你最在意的是稳定性还是便利性。我的经验是：先按上面的检查清单在 WebDAV 上跑一遍，确认它满足你的实际用法，再决定要不要换。
