# 多用户机器上的盘符映射：为什么「我这边好好的，你那边报盘符已存在」

> 说明：本文整理的是我在 Windows 11 + 多用户共用工作机（开发账号 + 运维账号 + 临时访客账号）上给本地目录分配盘符时实际踩到的几个坑。不同映射工具的实现细节会有差异，遇到类似现象建议按本文顺序排查一遍。

## 一、先分清两件完全不同的事

很多人第一次遇到盘符冲突时，会把下面两件事混成一件：

1. **盘符映射本身**：把某个目录挂成一个盘符（X: → D:\Projects\workspace）；
2. **网络驱动器映射**：把一个远程共享挂成一个盘符（Y: → \\nas\share）。

前者是纯本地的语义——`GetDriveType` 返回 `DRIVE_FIXED`；后者返回 `DRIVE_REMOTE`，很多程序（尤其是老旧的构建脚本、备份软件、杀毒软件）会因为这一条区别走完全不同的分支。

我见过最坑的一次情况：某台机器上 Y: 是网络驱动器，脚本里写了绝对路径 `Y:\build`，某天有人把 Y: 改成了本地映射，脚本照样能跑，但产出的文件落在了本地磁盘的某个目录里——构建产物凭空"换了个地方"。

排查第一步永远是先确认这个盘符到底是什么类型，而不是先怀疑文件丢了。

## 二、盘符分配顺序会造成「集体位移」

内置的 `subst` 和大多数映射器在分配盘符时，遵循的是「按字母从小到大找空位」的逻辑。于是：

- 机器上原本有 C: D: E:；
- 你给第一个目录分配了 F:；
- 后来又给第二个目录分配了盘符，工具重新扫描发现 F: 已被占用，于是分配了 G:；
- 结果配置里"第二个目录"的盘符从 E: 变成了 G:，而所有写死 E: 的脚本集体失效。

更隐蔽的情况是：某个映射器重启后按自己的配置顺序重新分配，顺序和你以为的不一样，盘符整体错位一格。

我的做法是**永远不把盘符写进配置和脚本**。配置里存逻辑名（比如 `workspace`、`assets`），运行时再把逻辑名解析成当前实际的盘符：

```
# 伪代码
logical = "workspace"
drive  = resolve_drive(logical)   # 查当前映射表
path  = f"{drive}\\build"
```

这样不管盘符怎么漂移，脚本引用的永远是当前真实存在的那个盘符。

## 三、改名之后映射还在，但读写报的是「设备未就绪」

目录改名或被移动之后，映射本身还挂在盘符上——盘符图标还在、资源管理器能打开、里面是空的。但程序往里写文件时报的是：

```
系统找不到指定的路径。
```
或者更让人抓狂的：
```
设备未就绪。
```

两种报错的差别很大：

- 「路径不存在」通常意味着目标路径确实没了；
- 「设备未就绪」往往意味着路径变了，但映射器还拿着旧的设备句柄，它自己也没意识到目标已经挪了窝。

后者才是真正耗时间的那一种。我处理它的方式是：**打开映射时先做一次存在性检查**，目标目录不存在就跳过并写一行日志，绝不阻塞登录、也绝不让程序挂在那儿等一个永远不会成功的 IO：

```
for name, target in config.mappings():
    if not os.path.isdir(target):
        log.warning("skip mapping %s -> %s (target missing)", name, target)
        continue
    mount(name, target)
```

这一条检查把「应用一启动就卡死十分钟」变成了「一行警告」。

## 四、退出时没释放盘符，下次启动直接冲突

映射器异常退出（崩溃、被杀进程、机器断电）之后，盘符在系统层面仍然是「已占用」状态。下次启动时映射器尝试创建同名盘符，会得到：

```
盘符已存在。
```

而此时那个占着盘符的其实是个僵尸映射——目标目录可能早就没了。

处理办法是启动时先释放再重建：对所有要用的盘符先调一次删除定义的 API，删不掉就打日志说明原因，然后继续创建。这一步不能省，因为省掉之后的表现是「程序以为映射成功，实际写进了错误的位置」——比直接报错危险得多。

## 五、多用户环境下，映射的归属必须显式

共享机器上最容易出事的一点：**映射到底属于哪个用户会话**。

如果映射不区分作用域：

- 用户 A 登录，映射了 W:；
- 用户 B 登录，也想映射 W:，工具提示「已存在」，于是 B 以为映射成功，其实他用的是 A 留下的那个映射——A 的目录；
- 于是 B 把自己的构建产物写进了 A 的工作目录。

这类问题往往要到某天清理空间时才被发现。

所以我的做法是：**作用域键 = 机器名 + 用户名 + 逻辑名**，并且启动时把映射归属打印出来：

```
scsmap list
# workspace  -> W:  (scope: HOST-01\alice)
```

再配一个开机自检：某个用户会话里发现别的用户的同名映射，直接跳过并提示，而不是默默复用。

## 六、什么时候值得自己写一个

如果你的场景里下面这三条里有任意两条：

- 开机就要有盘符；
- 脚本要稳定引用一个路径；
- 机器是多用户共用的；

那就值得上一个专门的映射器，而不是每次手动 `subst` 一遍。

但也别过度设计。我的经验是：一个只有三个功能的小工具足够——`add`（加一条映射）、`list`（打印当前生效映射）、`remove`（释放盘符），加上上面说的那个存在性检查和作用域键，就能覆盖绝大多数场景。

我自己用的工具是 ScsSubst（官网 https://subst.scsoi.com），做的就是「给已有目录分配独立盘符、开机自动恢复」这件事。
